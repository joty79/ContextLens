<h1 align="center">ContextLens</h1>

<p align="center">
  <b>Explorer context menu tools for OCR and clipboard image capture.</b><br>
  <sub>Right-click image and folder workflows for Lens OCR, saved clipboard images, and maintenance updates.</sub>
</p>

## What's Inside

| # | Tool | Description |
|:-:|------|-------------|
| 1 | **[OCR File](#ocr-file)** | Run Lens OCR on a selected image and save a sibling TXT file. |
| 2 | **[OCR Clipboard](#ocr-clipboard)** | Read an image from the clipboard and save OCR text in the current folder. |
| 3 | **[Save Clipboard Image](#save-clipboard-image)** | Save the current clipboard image as a timestamped PNG. |
| 4 | **[ContextLens Manager](#contextlens-manager)** | Open the app UI with update status and update submenu. |

## OCR File

> Converts a selected image into a TXT file through `lens_scan.exe`.

### The Problem

- OCR context menu actions were split across folders.
- Script paths and icons were hardcoded to machine-local locations.
- The old file action was installed separately from clipboard actions.

### The Solution

ContextLens uses one dispatcher script and one hidden launcher for Explorer verbs.

```text
Explorer image menu -> Launch-ContextLens.vbs -> Invoke-ContextLens.ps1 -> lens_scan.exe -> *_OCR.txt
```

### Usage

**From Explorer** — right-click a PNG image and choose `ContextLens` > `OCR image to TXT`.

**From terminal:**

```powershell
.\Invoke-ContextLens.ps1 -Action OcrFile -TargetPath 'C:\Path\image.png'
```

## OCR Clipboard

> Saves clipboard OCR output into the folder where the context menu was opened.

```text
Folder background menu -> ContextLens -> OCR clipboard to TXT -> Clipboard_OCR_yyyyMMdd_HHmmss.txt
```

## Save Clipboard Image

> Saves the current clipboard image into the folder where the context menu was opened.

```text
Folder background menu -> ContextLens -> Save clipboard image -> clipboard_image_yyyyMMdd_HHmmss.png
```

## ContextLens Manager

> Opens the ContextLens app UI in Windows Terminal.

| Action | What it does |
|--------|--------------|
| `Update app` | Shows current/latest version, commits, source, method, and runs the update backend in place. |
| `Open install logs` | Opens `logs\installer.log` if it exists. |
| `Open install folder` | Opens the current app root in Explorer. |

## Installation

### Quick Setup

```powershell
# Generate or refresh Install.ps1 from InstallerCore first, then:
.\Install.ps1 -Action Install -PackageSource Local -Force

# Update installed copy from GitHub:
.\Install.ps1 -Action UpdateGitHub -Force -NoExplorerRestart

# Uninstall:
.\Install.ps1 -Action Uninstall -Force
```

### Requirements

| Requirement | Details |
|-------------|---------|
| OS | Windows 10/11 |
| Runtime | PowerShell 7 for installer and manager; Windows PowerShell-compatible dispatcher |
| OCR engine | `lens_scan.exe` in `assets\bin` or `CONTEXTLENS_LENS_SCAN` |
| Explorer integration | Per-user registry keys under `HKCU\Software\Classes` |

## Technical Notes

<details>
<summary><b>Where does lens_scan.exe come from?</b></summary>

ContextLens first checks `CONTEXTLENS_LENS_SCAN`, then `assets\bin\lens_scan.exe`, then the legacy local Lens environment path. The repo should eventually own the runtime binary under `assets\bin` if redistribution is allowed.

</details>

<details>
<summary><b>Why use HKCU instead of HKCR?</b></summary>

The installer writes per-user context menu keys under `HKCU\Software\Classes` so normal install/update flows do not require elevation.

</details>

<details>
<summary><b>What happened to the old Lens and SaveClipboardImage entries?</b></summary>

The InstallerCore profile removes legacy Lens and SaveClipboardImage registry keys during install/update. Existing HKCR machine-level entries may require elevation for cleanup if they were imported from an old `.reg` file.

</details>
